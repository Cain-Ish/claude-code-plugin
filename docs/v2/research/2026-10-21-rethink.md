# Rethink: what we have learned, and what the plugin is for

Asked by the user on 2026-10-21, after three framing messages in two days (onboarding, the test bed, any stack):
step back, say what has been learned and what the plugin's idea is, then go on. Per rule 9, this note checks the
plan against the main idea and goes back where an assumption is unverified.

Sources: V2-D12 and V2-D17 results (DECISIONS.md, `probes/`), research notes of 2026-10-20 (scale, adherence,
literature), the Claude Code memory docs (https://code.claude.com/docs/en/memory, fetched 2026-10-21).

## 1. The idea, in the user's words

Claude does the architecture, planning, coding and review of a project in any language. Every project has decided
things along the way: its concept, its end goal, its rules and decisions, held by its developer, PM, designer or
marketer. When one of them changes or creates a small part, they remember what binds that part and know where to look
for the rest. Claude does not: it misses what was decided, or has it and does not apply it. The plugin makes Claude
work like the creator: for the part it touches, it has what was decided, finds the rest when needed, follows it, and
records what is newly decided. It starts from what the repo already has.

## 3. What v2 does not rebuild

- Capture of decisions spoken to one person (auto memory does it).
- Planning, architecture, coding and review (Claude does them; general code review stays a non-goal).
- Anything specific to one language (any stack).
- Commands defined in a repo's map (public plugin, D18).

What v2 adds, each still to be shown:
- knowledge read in documents or decided during work, kept with its source and shared through the repo;
- the part of a large body that binds the task, delivered before the work and into planning and review;
- holding Claude to it: checked where the project's tools or a data pattern can decide, accounted for where not;
- onboarding from what the repo already has.

## 4. The premise nobody has checked

Every adherence number we hold comes from somewhere else: the A1 fixture, the literature, v1's history and the
user's account. Nobody has run Claude in P1, P2 or the v1 repo as they are run today. If those setups already find
and follow their own rules, v2's case there is cost and knowing where to look, not adherence. A delivery gate and
checks would then be built for a failure that does not happen in these repos. The charter already says the baselines
run first; D19's native baseline was noted two days ago as runnable at any time, and it has not run.

## 5. The change

D20 splits in two stages:

- **Stage 1**, the premise: the native arm only, the repo as it is run today with its own rules and hooks. One task
  per test-bed repo, plus one planning or review task. For each task, the rules that bind it are chosen so that each
  leaves a decidable trace in the output. A rule that only judgment can score does not count, since D17 rejected an
  LLM judge; if a task's canon or design rule cannot be made decidable, pick another task. For each rule the run
  misses, the failure chain records whether it was never loaded, loaded but not read, or read but not applied. The
  same runs are D19's native baseline.
- **Stage 2**, the mechanism: arms built only for the kinds of failure stage 1 shows.
