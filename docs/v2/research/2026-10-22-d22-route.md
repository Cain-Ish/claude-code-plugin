# D22 route rethink, after the pull check (2026-10-22)

**Why this note.** D22 (selection) has been BLOCKED since 2026-10-21. It was waiting on the user to tick the essential
entries of six investigation tasks. Rethink 2 widened its options, and the pull check, its re-run with the web on and
attempt 3's count have now run ([DECISIONS.md](../DECISIONS.md), V2-D22). The user asked on 2026-10-22 that
decisions be settled by rethinking, checking the concept and a second opinion, without waiting on them. This note
does that for D22's route. Numbers are counts from the ledger. P1 and P2 are private repos, named only by count.

## 2. Where the forced route's tokens go

From the saved P2 sessions with the web on (medians, all turns):
- **Main thread:** `pf` 6.9M tokens, push 4.9M, native 6.2M. The forced route costs the main thread about 40% over
  push, and about 10% over native.
- **Subagents:** `pf` 7.3M, push 0.1M, native 1.7M. This is most of the gap, and its spread is large (1.1M to 25.7M
  in `pf`). The forced decision sends Claude to delegate research. In P2, that research was the outside canon check
  its own rules ask for.
- **Documents read in the main thread:** `pf` 7 to 10 per session (102 to 147 KB), push 3 to 5 (36 to 83 KB), native
  5 to 8 (66 to 110 KB).
- **P1:** `pf` read the same 4 documents (39 KB) in every session. Its main thread used 1.0 to 1.3M tokens against
  push's 0.9 to 1.3M, with almost no subagent use.

So the forced route's own price, more documents read in the main thread, is moderate. The large P2 figure comes
from the subagent research it triggers, which is variable.

A measure note, corrected at the phase gate: the harness's "read before the first write" counts a read in any thread,
and a subagent's read does not put the text in the main context (D12). The first version of this note said that, by
hand, every following session read the source in the main thread. That was wrong. In P2, R5 was read in the main
thread in 3 of the 5 `pf` sessions that followed it and R7 in 3 of 4; the rest were read by a subagent that
reported back ([mainreads.mjs](../probes/V2-D20-adherence/mainreads.mjs)). The asymmetry clause names no thread, so
no verdict changes. Some of the route's P2 reach is delegated reading, though, which matters for any variant that
keeps the reading in the session.

## 3. Reading

- The forced pull is the only route that reaches the missed rules **without an oracle**. It does so by Claude's own
  choice from a small index, which is what the charter describes ("Claude always sees a small index and reads a
  branch of the map only when the task touches it").
- Push of the exact set stays the cheapest and the best tested, also across a compaction. But every selector that
  could produce that set failed on reach.
- The two compose. Pull selects; what Claude read can then be re-pinned by push after a compaction, because a
  compaction drops read files that were not recent (D12) while hook text can be re-emitted.
- Path keys must come from onboarding, not from the documents (attempt 3's count).

## 4. Open before a lock

- **Generalisation.** 10 sessions on two build tasks, both already seen by every design step. A check needs tasks no
  design step has seen (D22's own constraint), and the third repo (R0, public).
- **Long sessions.** A forced decision at the first prompt does not cover the fifth prompt of a session that changed
  task, or a session after a compaction.
- **Index of what.** The pull check indexed raw documents. The charter's index is of the map. Under the user's
  "everything" scope, the map is about as large as the documents (D15), so pointing at the map does not by itself
  shorten reads.
- **Investigation tasks.** The six tasks the user wrote have no file to check. The judge's essential sets were never
  validated.

## 5. Second opinion (Gemini, 2026-10-22)

Gemini (Pro account, its most capable model, high thinking) got the table in section 1 as counts, with no private
text, and five questions. Its points, and how each was weighed:

- **"The forced route makes main-thread Opus the selector, at directory granularity."** Accepted as a framing. The
  forced text tells Claude to read every document in a directory it marks yes. At scale (50 directories, 300
  documents) that over-reads, and a file-level checklist would be too long.
- **"The P2 cost comes from documents injected into the main context."** Not supported by the split in section 2:
  the main thread costs about 40% more than push, and subagent research is most of the gap. The conclusion still
  holds, though: shorter map branches would not close a gap that comes from subagents.
- **"Push selection was killed by a broken metric."** Accepted, and it is the point that changes the plan. Every
  selector was scored against an LLM judge's essential sets on investigation tasks. None was run end to end on the
  build tasks with their deterministic checks. The volume check shows 32 KB of near-topic text costs no following.
  So a high-recall pick within about 30 KB may be enough. The saved picks stop short on their own: 11 to 60 entries,
  4 to 8 KB, often under the cap. So "high recall" needs a pick told to include more, not just a larger cap.
- **"Retire the judge's reach measure."** Accepted. It measured recall against a set nobody validated, and it gated
  every D22 attempt. End-to-end checks replace it: rule checks on the written files, task success, and tokens. For
  tasks that write nothing, assertions on the final answer or plan, including planted traps where a stale document
  or pre-training points one way and a binding rule points the other.
- **"Select out of band, per prompt, with a fast model (Haiku), seeing the files read recently."** Weighed against
  D18. D18 locked a budget of 100 ms per hook, and a model call takes seconds (the saved picks took 4 to 18 s). A
  pick in `UserPromptSubmit` fires D18's trigger, so the route has to pay that latency or run the pick only when the
  task changes. Gemini's estimate of under 800 ms is not measured.
- **Its three falsifying checks:**
  1. map branches instead of raw documents under the forced route (cost);
  2. a vague first prompt that pivots to the build in the second (does a first-prompt-only decision hold?);
  3. a high-recall pick pushed at the first prompt, head to head with the forced route.

  Number 3 has the most leverage, because if it holds, it dominates on cost. It also has a free count before any
  session. Number 2 tests every first-prompt route, push and pull alike, so it follows. Number 1 has the least
  leverage, given section 2.

## 6. What follows

- After it (2026-10-22): the high-recall count failed, so the forced route leads. The next check is the forced route

  slice's eval and named as a trigger, because no comparator exists for it yet.
- The route then locks on end-to-end evidence, with its cost: a pick's latency per task against the forced route's
  tokens.
