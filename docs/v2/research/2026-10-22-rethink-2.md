# Rethink 2: the findings against real sessions and the second-brain idea

Asked by the user on 2026-10-22, after D19 locked: rethink the findings before anything is built on them. Per rule
9, this note checks each recent finding's assumptions against the main idea and against how the plugin will actually
be used. It changes no locked record; it names what reopens and what the new check would measure.

Sources: the ledger ([DECISIONS.md](../DECISIONS.md)) and probes; the user's own Claude Code sessions on this machine
(numeric fields only, see §2); earlier research notes; the web sources listed at the end.

## 1. The correction, in the user's words (spelling corrected)

In the second-brain approach, context and information are kept in Markdown files so that Claude can always reach
them. How to hold Claude to the rules without filling up its context is a second issue that still needs research and
a solution, and the same goes for the other findings. Rethink them, and look for more information, so that nothing is
built on a wrong assumption.

The reading taken here: "always accessible" means the knowledge sits in files Claude can open whenever a task needs
it (pull), with a small part always loaded, which is the charter's "on demand, cheap" line. The open problem is
getting the binding part in front of Claude at the right moment, and keeping it there, at a cost the context can
carry. That a single task does not fill the window settles neither.

## 2. The count that discriminates: real sessions against probe sessions

D19 concluded that context does not fill, from 57 probe sessions: one headless prompt each, in a fresh clone, Sonnet
5.5, the largest turn at most 17% of the 1,000,000-token window, no compaction. The user's own sessions in P1 on this
machine were counted the same way (numbers only; no content read; 25 transcripts, of which 11 are working sessions of
20 or more turns; the others are one-turn helper sessions).

| | Probe sessions (D19, D20, D22) | The user's working sessions in P1 |
| --- | --- | --- |
| Shape | One prompt, headless | Interactive, median 74 turns (90th percentile 459), median 6.6 hours |
| Model | Sonnet 5.5 | Opus 5.5 and Fable 5.1 |
| Largest context of any turn | 34k to 170k tokens | median 548k, 90th percentile 838k, max 958k; 10 of 11 above 200k |
| Compaction | none in 57 | 7 of 11 sessions, 9 automatic compactions, at 223k to 839k tokens, each leaving 11k to 29k |

This project's own working sessions show the same pattern: the longest compacted 8 times.

The user is a heavier case than the population, not an outlier in kind. Across 2,676 Claude Code sessions from 43
developers, the context per step had a median of 126k tokens and a 90th percentile of 467k; 99.6% of steps grew it;
4.5% of sessions compacted [TRACELAB]. Our largest probe turn (170k) sits near that median. The docs put automatic
compaction near 967k tokens on a 1M window [CC-MODEL]; the user's compactions came at 223k to 839k, which compaction
on idle (D14's note on v2.1.299) may explain. Not checked.

**What this means.** The probes measured a task, not a session. The user works in sessions that fill most of the
window and are compacted to 1 to 3% of it. After a compaction, what survives from disk is the root instruction file,
unscoped rules and auto memory; path rules come back only when a file is touched again, and earlier hook output is
summarised (D12; the context-window docs). So any rule v2 delivers at prompt time or on a file read is lost at the next
compaction unless it is delivered again. D19's "context fill is recorded, not thresholded" answered the window-limit
question, which nobody asked; the user's question is what it costs to keep the binding rules in front of Claude
through a long session. That is a framing error in D19's check, not a dispute about its numbers.

## 3. What outside evidence says (two research passes and Gemini, 2026-10-22)

Two web-research passes (sources at the end) and one second opinion from Gemini (the Argon model in the Pro app). Gemini
had no live search in that session, so its figures are unsourced and are used only where a source below confirms them.
Several figures come from arXiv abstracts or summarised HTML pages. Any decision that rests on one quotes the paper
first.

**Context costs quality well below the window.**
- Length alone lowers accuracy, even with perfect retrieval or whitespace filler [DU] [CONTEXT-ROT].
- How far it falls depends heavily on the model generation. On one long-context test at 128k to 256k tokens, Sonnet
  4.5 scored 10.8 and Sonnet 4.6 scored 90.6; Sonnet 4.6 fell to 65.1 at 256k to 1M [SONNET46-CARD]. Most models
  lose accuracy roughly linearly in log-length from 8k to 128k [ATLAS].
- Our probes ran Sonnet 5.5; the user works on Opus 5.5 and Fable 5.1. A result on one model says little about
  another (D17's epoch rule already says so).

**Rules decay over a session.**
- Spreading a task over turns cost 39% on average, even at two turns [LOST-CONV].
- In 1,650 Claude Code sessions, the odds of following one trivial rule fell about 5.6% with each function written
  [MCMILLAN].
- Prohibitions decay while requirements hold, and re-injecting the rules restores compliance [OMISSION].
- Claude Code's own docs: as context fills, Claude "may start forgetting earlier instructions" [CC-BEST].

**Compaction drops rules unless they are re-delivered.**
- In Claude Code, the root instruction file, unscoped rules and auto memory come back from disk. Path rules come back
  only when a matching file is touched again. Hook output is summarised unless a session-start hook on `compact`
  re-adds it. Instructions given only in conversation are lost [CC-CONTEXT].
- Compactors keep 17% of injected constraints on average. In one agent, a forbidden action happened in 30 of 100
  sessions after compaction and in none before; restating the constraint after compaction cut that to 13% [LCC].
  In another study, violations went from 0% to 30% after compaction and back to 0% once the constraints were pinned
  [GOV-DECAY].
- No source measures how many rules Claude Code's own compactor keeps.

**Push beats agent-chosen pull for compliance, but an always-on index can make pull work.**
- Vercel [VERCEL]:
  - a docs skill left alone: 53% pass, the same as no docs; it was never invoked in 56% of cases;
  - the skill plus an instruction to use it: 79%;
  - an always-on 8 KB index of the docs' file names, plus the instruction "prefer retrieval-led reasoning over
    pre-training-led reasoning": 100%. The agent read the docs themselves with file tools.
- Claude Code invoked task skills in 68% of trials with Opus 4.7 [SKILLSBENCH]. With 83 skills available and no
  instruction, it read a skill in 0 of 40 audits with Opus 4.8 [EVMBENCH].
- A prompt-time hook that makes Claude state, skill by skill, whether it applies and then call it, reached 100%
  activation in two runs of 22 prompts each. A plain reminder did no better than no hook [SPENCE].
- What triggers a skill is the prompt's own words, not the skill's text [SPENCE]. Anthropic says Claude
  "undertriggers" skills [SKILL-CREATOR]. Its docs say a pointer in `CLAUDE.md` is read only if Claude decides to
  open the file [CC-MEMORY].
- No study measured naming by task against naming by topic.

**More delivered text costs task success and money.**
- Developer-written context files raised success by 4% on average, but not for Claude Code, and cost up to 19 to 23%
  more [ETH].
- All-rule compliance falls as rules are added: 0.95 with one rule, 0.48 with ten [MANYIF]. Stacking 1 to 20 rules
  fell to as low as 20% [STACKING].
- 30 or more "don'ts" doubled the time and cut completeness by 20%. The best files had 100 to 150 lines and at most
  10 to 15 references [AUGMENT].
- Compact skills added 19 points; comprehensive docs packed as a skill added 0.7 [SKILLSBENCH].
- A flat, one-level index helped; a second routing level never did [PROG-DISC].

**Gemini's review**, pointed and consistent with the sources above:
- In a long session, prompt arrival may be 40 tool calls and a compaction away from the edit. So deliver a short rule
  at the action (matched by the written file's path), and re-pin the binding rules after each compaction.
- Keep the imperative rule apart from its rationale and rejected options, which stay on disk until someone asks.
- Do not trust the model to browse a topic hierarchy for rules.

## 5. What reopens, and what the next check would measure

Nothing here edits a locked record; the reopen is the next step, once the user has read this. Under rule 9 the user's
judgement that the framing was wrong goes back to the decisions it rests on. D12's own trigger also fired ("a design
depends on a context not probed here: an interactive session, another model").

1. **A session check first (reopens D19's context measure and D20's timing; D12 for interactive sessions).** It should
   be one long session on the user's model, several prompts, enough tool output to cross a forced compaction (D12's
   `/compact` probe note), and rules whose checks already exist (D20's 27). Per rule, compliance before and after the
   compaction, by delivery path:
   - native;
   - text at prompt arrival (D20's c);
   - a short rule at the action, keyed by the written path (the deny D18 dropped, re-scoped);
   - re-delivery on compact.

   Also count tokens per request, requests per session, re-delivered bytes, task success and cost. This settles
   whether prompt-time delivery survives real use, before selection is re-scored.
2. **D22's options widened before its re-score.** Add the shapes the evidence supports and the ledger never ran:
   - Vercel's: an always-on compact index of the map with a retrieval-led instruction;
   - a forced decision at prompt arrival, where Claude names which areas bind and reads them;
   - path-keyed delivery at the action.

   The user's ticks still decide the essential sets.
3. **Volume as a measure (D13, D15, D20).** Task success and cost against the number and length of the rules
   delivered, the imperative rule alone against the rule with its rationale. This tests the user's "everything"
   scope against the evidence that more text costs success.
4. **Baselines on the user's model** (D17's epoch rule) before thresholds are used: A1 and A2 ran on Sonnet 5.5.

## 6. Limits

- The real-session count covers one user, on one machine, in one private repo plus this project: 11 working sessions.
  It shows the shape of real use, not a population.
- Prompts per session were counted by a heuristic. Turns and hours are the firmer figures.
- Several outside numbers are from abstracts or summarised pages, or from single-author preprints. Vercel's figures
  are a vendor's, without model or run counts. No source measured Claude Code's own compactor.
- Gemini's answer had no live search. Its points enter only where a source above agrees.
