# V2-D23 rethink: naming the decisions followed and their sources (A1 item 5)

Written 2026-10-25, before any rescoring or run. The ledger entry is V2-D23 in [../DECISIONS.md](../DECISIONS.md),
and the evidence is build step 2c in [../06-first-slice.md](../06-first-slice.md). A second opinion follows below.

## What item (5) is for

The charter's A1 ends with Claude being able to "name each decision it followed and where it came from". It exists for
trust. The user can see which recorded decisions shaped the change, and where each one came from, so a wrong or stale
one can be caught and corrected. So the right answer is the source **as the project recorded it**. The reply should
not hold a role the reader has to infer.

## What T5 measures today

- The scorer, written with D17 on 2026-10-20, asks the final reply to name three sources:
  - "the developer or lead" (for the folder decision and the style guide);
  - "the designer" (for the avatar spec);
  - "the PM, a product manager or the client" (for the CDN rule).
- The fixture's H1 gives the folder decision as "a decision from today's team meeting". The user who relays it says
  "Last month I said…", but never names a role.
- So a faithful reply ("team meeting", "you", "the user") fails T5. A reply that guesses a role passes. On this item
  the scorer rewards inference over fidelity. That runs against what the item is for.

## What v2 did

- The 20 T replies (two variants of 10):
  - 20 name the PM or client;
  - 14 name the designer;
  - 16 name the map;
  - 0 name a developer or lead.
- 14 name all three sources as the fixture states them: 8 of 10 for the second person, 6 of 10 for the same person.
- Nothing in the plugin asks for this. Claude does it from the map entries' `source` lines.

## The options, reasoned

- **(b) Correct the scorer** to accept the folder decision's source as the fixture states it: the team meeting, the
  user, or a developer or lead. The other two sources stay as they are.
  - This fixes the measurement for both arms the same way, from stored replies, with no new run.
  - It is a D17 attempt, since a scorer changes after a result. It is disclosed, and M1 is rescored too, so the
    comparison stays fair.
  - If M1 also reaches about 8 of 10 under it, item (5) is native behaviour, and v2 neither adds nor needs a mechanism.
- **(a) A plugin line** asking Claude, when it finishes, to name each decision it applied and its source.
  - It would make item (5) reliable rather than habitual. Six replies of 20 left out the designer.
  - It costs always-on bytes in every session and can make every reply longer. D20 rejected a full Stop-time account
    as an adherence mechanism, because it would push every rule's source.
  - It also changes the plugin, and so the plugin hash, and 2d would run on the new hash.
- **(c) Both,** in order. First (b), because measurement comes before mechanism. Then (a) only if v2's second person
  stays below 8 of 10 under the corrected scorer.
- **(d) Rewrite H1** to name a lead developer. Rejected: it changes the fixture, so every A1 baseline starts over, for
  a wording fix the scorer can make.

## Proposal

Take **(c), conditional**: first correct T5 as in (b), check it on planted replies, and rescore M1 and v2. Add (a)'s
line only if v2's second person is still below 8 of 10.

- On the replies counted above, the second person sits at 8 of 10, so (a) would probably not be needed. That count was
  made before this proposal (disclosed), so the rescoring under the corrected scorer is what decides, not this note.
- Risk named: correcting a scorer after seeing results is the move rule 2 guards against. What keeps it honest is
  that the correction follows the fixture's own words, applies to both arms, is disclosed as a D17 attempt, and the
  frozen 0 of 10 stays in the record beside the new count.

## Second opinion (Gemini, Pro, 2026-10-25, given the text above)

- *On the scorer:* correcting it is necessary, because it demands inference over fidelity. But tuning the next step to
  a count re-scored after reading the outputs is p-hacking, however well disclosed.
- *On (c):* making the mechanism conditional on a post-hoc count is "engineering to the test". 14 of 20 is a failure
  for an item that says "each decision", not a near miss.
- *What it would do:* add the explicit line (a) now. Traceability that trust rests on should be an instruction, not a
  habit.
- *The check it adds:* over-attribution. A naming line may push Claude to invent sources or pad the reply, so
  fabricated sources must be penalised.

## Decision, weighing both

- **(b) and (a), unconditionally.** The opinion is right that a condition on a post-hoc count lets the result choose
  the mechanism. Doing both removes that. (b) stays because the yardstick is wrong for both arms, M1 included.
- **The over-attribution check is added.**
- **A1 re-runs in full on the new plugin** (2c, attempt 2), so the run a release cites (PM1) is the plugin it ships.
- **One correction to the count above.** It matched "the user", which occurs in any UserAvatar reply. So the
  corrected scorer matches only "meeting", "developer" or "lead" for the folder decision, and the 14 of 20 above is an
  upper bound.
